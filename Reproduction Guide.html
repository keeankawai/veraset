Reproduction Guide

Companion to Results Write-Up. It goes through the write-up label by label (paragraph labels like 2.2a, tables T…, figures F…) and says where each result is computed, which file holds it, and what to edit to change the assumption behind it. Every reference is a line number in a script in tools/, written make_step4.py:316 (one line) or make_step4.py:316–366 (a range). The scripts also carry comments starting with Write-up: that point back to the sections below.

A. How the code is organized, and how to rebuild

Each step is a script in tools/ that writes a Jupyter notebook in Task 1/; running the notebook (from the project root, since its paths are relative to it) produces the step's tables in processed-data/. The code that runs is the text inside each code("""…""") block of the script, in the same order as in the notebook, so a line number in the script is the place to read or edit. Edit the script, not the notebook: regenerating the notebook overwrites hand edits. The make_step*.py scripts (and step2_cells.py) are kept locally and are not in the git repository (they are gitignored); the notebooks are. The notebooks are named by run order (step1_ to step6_), which is not the same as the table labels: Task 1/step1_geography_helpers_processing.ipynb builds the [3…] tables, because Steps 1 and 2 read them. Printed results (counts, tables) are in the notebook's output under the code that prints them, so "printed at make_step4.py:365" means: open the notebook, find the block containing that line, and read its output.

Run the notebooks in the order of their prefixes, step1_ to step6_: geography (table labels [3]), WSLCB stores ([1]), Veraset devices ([2]), dispensary visits ([4]), visits and access ([5]), store coverage ([6]). Each reads the tables of the ones before it; step6_ only needs step1_ and step2_. From the project root (prefix any of these with python3 tools/make_stepN.py NOTEBOOK && to regenerate the notebook from its script first, if you have the scripts):

python3 tools/run_nb.py "Task 1/step1_geography_helpers_processing.ipynb"
python3 tools/run_nb.py "Task 1/step2_wslcb_safegraph_locations_processing.ipynb"
python3 tools/run_nb.py "Task 1/step3_veraset_devices_processing.ipynb"   # slow, see below
python3 tools/run_nb.py "Task 1/step4_dispensary_visits_processing.ipynb"
python3 tools/run_nb.py "Task 1/step5_visits_and_access_processing.ipynb"
python3 tools/run_nb.py "Task 1/step6_store_coverage_processing.ipynb"
python3 tools/build_writeup.py

step4_, step5_, and step6_ take well under a minute each; step2_ takes a few minutes. Task 1/step3_veraset_devices_processing.ipynb is slow, because it scans all of the raw Veraset data, and only needs rerunning if the sample definitions change. Charts are written to Charts and Figures/ every time step4_, step5_, and step6_ run; the write-up carries its own copies (so it works as a single file, offline), refreshed by tools/build_writeup.py. The write-up's numbers and prose are typed in, so after changing an assumption they have to be updated by hand from the tables listed below.

To look at any output table:

import polars as pl
pl.read_parquet("processed-data/4cii_visit_distributions.parquet").filter(pl.col("period") == "all")

C. The manual review: before, after, and what it changed

The only place a person labeled data by hand is the Step 1 store review. Everything else is computed.

What was reviewed. After the automatic checks (0.2b), every [1e] label whose name might be the store's but did not pass the automatic name rule was set to name_check = "review" and left out of the approved list. That covers four kinds of label: a tradename match with extra words, a cannabis word without a tradename match, only the cannabis category code, or any label at a different address (make_step1.py:1299–1316 and :1329–1383). build_review_1e.py grouped those rows into 258 items (:38–54), one per place ID, Veraset name, and WSLCB storefront, ordered by visits (:53). It wrote them into review/1e_review_page.html, which shows the Veraset label month by month, the WSLCB history at the address, and links to maps and searches. Each item was marked yes or no on that page, and the verdicts were exported to review/1e_review_verdicts.csv (columns safegraph_place_id, location_name, street_address_norm, city_norm, verdict, plus notes and context).

How the verdicts enter the pipeline. make_step1.py:1384–1397 reads the CSV if it exists and, for rows still marked "review", turns a yes into yes_in_review (:1390) and a no into no_in_review (:1391). A verdict cannot override a row that was already "auto" or "no". Approval then treats yes_in_review the same as "auto" (NAME_OK, :1326). The operating-license check still applies, so a yes only approves the months a license was operating there.

E. Things that are not fully reproducible, and small quirks

Typed-in prose. The write-up's numbers were copied from the tables above after the final run; they do not update themselves. The charts update when tools/build_writeup.py is rerun.

One-off numbers. The "about 7% of approved visits in one-sided months" (6b), and its breakdown in step1_future_fixes.md, came from an ad hoc calculation that no script reproduces. Every other number in the write-up comes from a printed output or table listed in section B.

A tie in Step 1. When two versions of a place's category code have the same number of visits in a month, which one is kept is not fixed (make_step1.py:1233), so rerunning Step 1 can change naics_code on a row or two of [1e]. A rerun during this work changed one row, which was not approved; approvals and visit counts were identical.

Raw [1e] visit counts are not cleaned. num_visits in [1e] counts rows in the raw monthly files, so it still includes the duplicates removed in 0.3 (and 7,401 visits are counted at two storefronts if you simply sum it). The 1,063,478 in 0.2d is that raw count. All results in sections 1–5 use the cleaned visits in [4bi]/[4bii].

A tie in the duplicate removal. A visit on the 1st of a month appears in two monthly folders with the same dwell, and which copy is kept is not fixed (make_step4.py:323). The copies differ only in month (the folder) and the store label fields that come with it, so a rerun can change those on a couple of thousand rows of [4bi]/[4bii] (1,785 in the yearly sample last time). Every result stays the same (the lowest operating license, which counts stores, is the same on both copies); the rerun for the 60-day stretch confirmed the yearly results were identical.

Step 2 has never been run from its script. make_step2.py is a copy of the existing notebook, checked to produce identical code, but the notebook's outputs come from the original hand-run notebook. Two of its blocks are scratch that does nothing for the results (make_step2.py:287, a test save, and :289, a look at one table).
